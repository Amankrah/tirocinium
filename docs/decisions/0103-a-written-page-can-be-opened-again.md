# 0103: a page written on the pad can be opened again and changed

A page added from the pad used to become a PNG in the list and nothing else, so a student who spotted a slip after adding it could only remove the page and write it out again. Each pad page now keeps the strokes it was drawn from beside its image, and tapping its thumbnail (or the pen control in its row, which is the one a keyboard or screen reader reaches, so the page is not announced twice) opens it on the pad with those strokes and no undo history behind them, so the first undo cannot blank the page being corrected. Saving replaces the page where it sits in the list, keeping its id and position and letting go of the old preview; cancelling leaves it exactly as it was; removing it or leaving "Write here" ends the edit; and Send waits, with a line saying why, while a page is open, because sending then would send the page as it was before the change. Editing is the same ink coming back rather than a photograph of the export drawn over, which keeps the page a single clean layer. Photographs and PDF pages have no strokes and are replaced, as before, by removing and adding. Building it exposed a defect in the failure path, fixed with it: a send that fails part-way holds the pages as they were when it started and retries page N of that list, so once the list changed (a page edited, moved, removed or added) a retry would send the wrong page; any change to the list now lets the failed attempt go, and Send starts a fresh one from the pages on screen. The panel's contract is pinned in `upload-panel-edit.test.tsx` with a stub pad, and the pad's own in `pen-pad.test.tsx`; the canvas repaint of an opened page is a browser behaviour jsdom cannot show and still wants a pass in the mode-C journey.
