# 0099: math delimiters are normalised at confirmation

Decision 0098 left one gap flagged: an imported problem confirmed into a case study kept the `\( \)` and `\[ \]` the transcription prompts write, so the reading surfaces rendered it correctly but auto-parameterization and variant generation, which read the case study body and the confirmed item's solution through `base_solution`, were handed delimiters the rest of the course does not use (the generation prompt writes dollars, so a variant could come back in a different notation from its base). Confirmation now rewrites both texts with `app/math_delimiters.py` before they are stored, because confirmation is the one place model output becomes course content, and every consumer downstream (proposal, generation, verification, the tutor, the unfold, the reading surfaces) reads from there. We normalise at that boundary rather than asking the prompts for dollars, for two reasons: brackets cannot be confused with a price, which a materials course quotes, and a staged reading stays exactly what the model wrote, so the import review shows the extraction rather than our rewrite of it. The rewrite changes delimiters only; the formula's own text passes through exactly, code is untouched, and an unpaired dollar beside a converted formula is escaped so that a price cannot pair with the new dollars and turn the sentence between them into maths. The edit-distance metric (decision 0030) is measured on the professor's text as written, before the rewrite, so normalisation never counts as a correction. The rule now exists twice, in Python here and in the web's `normalizeMath`, which still has to render text that never passes confirmation (staged items and student transcriptions); both test suites run one case table, `apps/api/tests/fixtures/math-delimiters.json`, so a change to one that the other does not share fails. Case studies confirmed before this change could still carry brackets, so `scripts/normalize_import_math.py` (logic in `app/imports/math_backfill.py`) applies the same function to exactly the two texts confirmation now rewrites, the body of a case study born from a confirmed item and that item's solution, never a staged reading, a course-pack body, or a hand-authored one. It reports by default and writes only with `--apply`, each course planned and written inside one writer transaction, and a second run finds nothing. The development data directory was checked on 2026-10-21 and needed nothing: of its seven imported case studies none carries a bracket, because they came from born-digital PDFs whose text layer holds no LaTeX at all, and no blob in any text column of the shard would change. The deployed host's data directory was checked the same day by running the report against `/var/lib/tirocinium/data` with the API up: one course scanned, no body and no solution to rewrite, so `--apply` was never run. Neither database held content that predates this decision in need of conversion; the script stays for any shard restored from an older backup.
